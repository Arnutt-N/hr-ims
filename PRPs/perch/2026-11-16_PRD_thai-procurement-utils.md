## 1. ปัญหา

HR-IMS เป็นระบบคลังพัสดุที่วิศวกรรมดี แต่**ไม่มีชั้นความถูกต้องทางระเบียบราชการเลย**

ตรวจจากโค้ดจริง ณ 2026-11-16:

| สิ่งที่ควรมี | ผลการค้น |
|---|---|
| `bahtText` (จำนวนเงินเป็นตัวอักษรไทย) | 0 ตรง |
| `fiscalYear` (ปีงบประมาณ ต.ค.–ก.ย.) | 0 ตรง |
| `taxId` (checksum 13 หลัก) | 0 ตรง |
| `withholding` / WHT | 0 ตรง |
| `VAT` | 0 ตรง |
| `thresholdRules` (เกณฑ์วงเงิน 4 ระดับ) | 0 ตรง |
| `addWorkingDays` (วันทำการ) | 0 ตรง |

ที่มีอยู่คือ `frontend/next-app/lib/date-utils.ts` (73 บรรทัด) ซึ่งมีแค่ พ.ศ. และรูปแบบวันที่ไทย
ไม่มีปีงบประมาณ ไม่มีวันทำการ ไม่มีเลขไทย

**ผลกระทบต่อผู้ใช้:** เจ้าหน้าที่ต้องคำนวณ VAT/WHT และเขียนจำนวนเงินเป็นตัวอักษรด้วยมือ
ทุกครั้งที่ออกเอกสาร ซึ่งเป็นจุดที่ผิดบ่อยที่สุดในงานพัสดุ และเมื่อผิดจะผิดทั้งใบสั่งซื้อ
ใบตรวจรับ และ 50 ทวิ พร้อมกัน

**ผลกระทบต่อนักพัฒนาคนถัดไป:** ทุกโมดูลพัสดุที่จะเขียนต่อ (ครุภัณฑ์, งบประมาณ, เอกสารพิมพ์)
ต้องเขียนสูตรพวกนี้ซ้ำเอง หรือแย่กว่านั้นคือลอกมาจากต้นแบบ Apps Script ที่มีข้อผิดพลาด
ซึ่ง spec ระบุไว้แล้วว่า**ห้ามทำ parity ตาม**

## 4. ขอบเขตฟังก์ชัน

### 4.1 `baht-text.ts` — จำนวนเงินเป็นตัวอักษรไทย

**ที่มา:** `egp/SPEC.md:759` (§4.10)

**สัญญา:** `bahtText(amount: number | string): string`

**กฎที่ต้องรองรับ:**
- หลักหน่วยเป็น 1 ที่มีหลักอื่นนำหน้า → "เอ็ด"
- หลักสิบ 2 → "ยี่สิบ", หลักสิบ 1 → "สิบ"
- เกินล้านอ่านซ้ำเป็นชุดละ 6 หลัก
- ไม่มีสตางค์ → ลงท้าย "บาทถ้วน"
- มีสตางค์ → "…บาท…สตางค์" (ปัดเศษ 2 ตำแหน่งก่อน)
- ติดลบ → throw

**Fixture จาก spec (ต้องผ่านทุกตัว):**

| อินพุต | ผลที่ต้องได้ |
|---|---|
| 32,394.39 | สามหมื่นสองพันสามร้อยเก้าสิบสี่บาทสามสิบเก้าสตางค์ |
| 305.61 | สามร้อยห้าบาทหกสิบเอ็ดสตางค์ |
| 21.00 | ยี่สิบเอ็ดบาทถ้วน |
| 0.50 | ห้าสิบสตางค์ |
| 1,000,001 | หนึ่งล้านเอ็ดบาทถ้วน |

**หมายเหตุ:** spec ระบุว่าบางหน่วยงานเขียน "หนึ่งล้านหนึ่งบาท" → ทำเป็น option ได้ในอนาคต
ไม่ใช่เฟสนี้

### 4.2 `tax-id.ts` — เลขประจำตัวผู้เสียภาษี 13 หลัก

**ที่มา:** `egp/SPEC.md:758`

**สัญญา:**
- `normalizeTaxId(input: string): string` — ตัดขีดและช่องว่าง
- `isValidTaxId(input: string): boolean`
- `taxIdSchema` — Zod schema สำหรับใช้ที่ boundary

**สูตร:**
```
sum = Σ d[i] × (13 − i)   สำหรับ i = 0..11
check = (11 − sum mod 11) mod 10
ต้องเท่ากับ d[12]
```

**ใช้ทั้ง client และ server** ตามที่ spec กำหนด (Zod ฝั่ง server, ฟังก์ชันเดียวกันฝั่ง client)

### 4.3 `vat-wht.ts` — VAT 7% และหัก ณ ที่จ่าย 1%

**ที่มา:** `egp/SPEC.md:686-707` + `ProcureHub:570-587`

**สัญญา:**
```ts
type VatMode = 'INCLUDED' | 'EXCLUDED' | 'EXEMPT'
type VendorType = 'JURISTIC' | 'INDIVIDUAL'

computeVat(input: { amount, mode, rate? }): { base, vat, total }
computeWht(input: { base, total, vendorType, isFarmProduce?, rate?, thresholdBasis?, threshold? }): { applies, wht, netPay, form }
```

> **เลื่อนไปเฟสถัดไป:** `priceCalcMode` (`PER_LINE` / `ON_TOTAL`) และการรวมยอดหลายบรรทัด
> (`lineAmount = qty × unitPrice`) **ไม่อยู่ในเฟสนี้** — `computeVat` รับยอดรวมก้อนเดียว
> ซึ่งพอสำหรับใบสั่งซื้อ/ใบตรวจรับที่คำนวณยอดรวมมาก่อนแล้ว
> การคิด VAT รายบรรทัดต้องมีตาราง line item ซึ่งเป็นงานของเฟสเอกสาร
> (spec: `egp/SPEC.md:692` กำหนด `PER_LINE` / `ON_TOTAL` ไว้ แต่ยังไม่ implement)

**สูตร VAT:**
```
INCLUDED : total = amount; base = total / 1.07; vat = total − base
EXCLUDED : base  = amount; vat = base × 0.07;   total = base + vat
EXEMPT   : base  = total = amount; vat = 0
```

(การปัดเศษ 2 ตำแหน่งทำที่ระดับสตางค์ภายใน ไม่ใช่ที่ระดับบรรทัด เพราะเฟสนี้รับยอดรวม)

**สูตร WHT:**
```
whtBase = base (ยอดก่อน VAT)
applies = (JURISTIC และ total ≥ 500) หรือ (INDIVIDUAL และ total ≥ 10,000)
          และไม่ใช่ isFarmProduce
wht     = applies ? round2(whtBase × rate) : 0
netPay  = total − wht
form    = JURISTIC ? 'ภ.ง.ด.53' : 'ภ.ง.ด.3'
```

**จุดที่ต้องระวังที่สุด — ต้นแบบทำผิด:**

`ProcureHub:570` ระบุตรง ๆ ว่า *"ต้นแบบใช้ 3% ซึ่งน่าจะผิดสำหรับหน่วยงานรัฐ"*
และให้เหตุผล 3 ข้อ:

1. หน่วยงานของรัฐหัก **1%** ทั้งซื้อและจ้าง · 3% เป็นอัตราของภาคเอกชน
2. ฐานต้องเป็นยอด**ก่อน VAT**
3. มีเกณฑ์ขั้นต่ำ 500 / 10,000 และยกเว้นพืชผลเกษตร

**ถ้าลอกต้นแบบตาม จะหักภาษีผู้ขายเกิน** ตัวอย่างเทียบจาก spec:

| ยอด | ต้นแบบ 3% ของยอดรวม | ที่ถูก 1% ของฐาน | ส่วนต่าง |
|---|---|---|---|
| 289,000.00 | 8,670.00 | 2,700.93 | **5,969.07 บาท** |

**Fixture จาก spec:**

| อินพุต | ผลที่ต้องได้ |
|---|---|
| 32,700.00 INCLUDED | base 30,560.75 · wht 305.61 · net 32,394.39 |
| 432,000.00 INCLUDED | vat 28,261.68 · base 403,738.32 · wht 4,037.38 · net 427,962.62 |
| 10,700.00 INCLUDED | base 10,000.00 · wht 100.00 · net 10,600.00 |
| 20,000 EXEMPT บุคคลธรรมดา | wht 200 · net 19,800 |
| 4,500 บุคคลธรรมดา | ไม่หัก |
| 10,000.00 EXCLUDED | vat 700.00 · total 10,700.00 |

**อัตราและเกณฑ์เก็บเป็น config ไม่ hard-code** ตามที่ spec กำหนด (`:696`)

### 4.4 `thresholds.ts` — เกณฑ์วงเงิน 4 ระดับ

**ที่มา:** `egp/SPEC.md:737-744`

**สัญญา:** `thresholdRules(amount: number, table?: readonly ThresholdRule[]): ThresholdRule`

| วงเงิน (บาท) | e-GP | ประกาศแผน | รูปแบบสัญญา | ผู้ตรวจรับ |
|---|---|---|---|---|
| ≤ 5,000 | ไม่ต้อง (ว 322) | ไม่ต้อง | ใบเสร็จ/ใบส่งของแทนสัญญาได้ | 1 คน หรือตรวจเอง |
| 5,001–100,000 | ขึ้นทะเบียน e-GP | ไม่ต้อง | PO/ข้อตกลง หรือใบเสร็จ (ม.96) | 1 คน |
| 100,001–500,000 | ทุกขั้นตอน | ไม่ต้อง | PO หรือสัญญามาตรฐาน | 1 คน หรือคณะ 3 คน |
| > 500,000 | e-market/e-bidding | ต้อง (ม.11) + รับฟัง TOR ≥ 3 วัน | สัญญาเต็ม (ม.93) + หลักประกัน 5% | คณะ ≥ 3 คน |

**ข้อจำกัดที่ต้องบันทึกในโค้ด:** spec ระบุว่าตัวเลขมาจาก*คู่มือต้นแบบ* ไม่ใช่ตัวพระราชบัญญัติ
(`:744`, `:934`) → ต้องเป็น **ค่าตั้งต้นที่ override ได้** ไม่ใช่ค่าตายตัว
และต้องมี comment เตือนให้ตรวจกับระเบียบฉบับล่าสุดก่อน go-live

## 5. ข้อจำกัดทางเทคนิค

| ข้อ | ค่า |
|---|---|
| ตำแหน่งไฟล์ | `frontend/next-app/lib/thai-procurement/` |
| Runtime | Node + browser (pure function ห้ามมี I/O) |
| Test runner | Vitest (ตาม `vitest.config.ts` ของโปรเจค) |
| Test location | `frontend/next-app/tests/lib/thai-procurement/` |
| Zod | ใช้เวอร์ชัน frontend (v4) |
| ตัวเลขเงิน | `number` ที่ระดับ API แต่คำนวณภายในด้วย integer สตางค์เพื่อกัน floating point |
| Import | ห้าม import `@/lib/prisma`, `next/*`, หรือ Server Action ใด ๆ |

**การตัดสินใจเรื่องความแม่นยำ:** `Float` เป็นจุดอ่อนที่รู้อยู่ของ HR-IMS (`estimatedCost Float?`)
เฟสนี้จึงคำนวณภายในด้วย **integer สตางค์** แล้วแปลงกลับเป็น number ที่ขอบ
ไม่ผูกกับ schema ที่ยังเป็น Float
