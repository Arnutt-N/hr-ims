## สรุปงานที่ทำ

Wire `maintenanceEscalationQueue` เข้า BullMQ bootstrap — ปิด gap ที่ escalation cron เขียนไว้แต่ไม่มี process รัน

**สิ่งที่ค้นพบก่อนทำ:** ตรวจแล้วพบว่า queues ทั้งหมดใน backend (escalation, backup, email) เป็น dead code — ไม่มีไฟล์ไหน import, `index.ts` ไม่เริ่ม worker ใดเลย จึงแก้ที่ root cause ด้วย dedicated worker entry point เดียวที่ host workers ทั้งสามตัว

## ไฟล์ที่สร้าง/แก้ไข

- `backend/src/worker.ts` (**ใหม่**) — entry point ของ background-worker process:
  - `dotenv.config()` **ก่อน** `require()` queue modules (static imports ถูก TS hoist ข้าม dotenv ทำให้อ่าน `REDIS_URL` ก่อน env โหลด — ใช้ require-style แก้)
  - เรียก `scheduleMaintenanceEscalation()` + `scheduleBackupJob()` (ทั้งคู่ clear-repeatables ก่อน add → restart-safe)
  - Graceful shutdown: SIGINT/SIGTERM → close workers (drain in-flight) + queues, force-exit fallback 10s
  - `WORKER_ENABLED=false` escape hatch
- `backend/package.json` — เพิ่ม `start:worker` (prod) / `dev:worker` (nodemon)
- `backend/src/queues/{maintenanceEscalationQueue,backupQueue,emailQueue}.ts` — เพิ่ม `maxRetriesPerRequest: null` บน connection (requirement ของ BullMQ Worker blocking commands) — config-only ไม่แตะ logic
- `backend/.env.example` (**ใหม่**) — template พร้อม doc `WORKER_ENABLED`, `MAINTENANCE_ESCALATION_CRON`
- `.gitignore` — เพิ่ม `!**/.env.example` (pattern เดิม `**/*.env.*` กลืนไฟล์ template)
- `AGENTS.md` — §6 ย้ายงาน → Completed, §2.2 เพิ่ม script docs

## ข้อควรระวัง / หมายเหตุ

⚠️ **Deployment breaking-ish:** prod ต้องรัน process ที่สอง (`npm run start:worker`) คู่กับ `npm start` — ไม่งั้น escalation/backup/email jobs ไม่ทำงาน (แต่ API ปกติ)

- Windows: Stop-Process ไม่ trigger SIGINT → graceful shutdown path ยังไม่ได้ทดสอบ live (logic ตรวจแล้ว, ใช้ pattern เดียวกับ index.ts)
- Pre-existing test failures (RBAC matrix 401s) ยังอยู่ — track แยกจากงานนี้
