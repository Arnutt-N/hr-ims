## การตัดสินใจและเหตุผล

### V20 — technician/auditor เห็น request ของทุกคน

**สิ่งที่พบ:** `requestController.getRequests` กรองเฉพาะเมื่อ `role === 'user'` เท่านั้น

**หลักฐานที่ชี้ขาด:** frontend บังคับ policy ที่เข้มกว่าอยู่แล้ว — `lib/actions/requests.ts:15-21` ใช้ `APPROVER_ROLES` (admin/superadmin/approver) และ scope คนอื่นด้วย `where.userId`

**ตัดสิน:** backend ใช้ approver tier เดียวกับ frontend
- technician ไม่มีอำนาจอนุมัติ (`requireRole` บน status route ไม่รวม role นี้) → เห็นของคนอื่นโดยไม่มีความรับผิดชอบคู่กัน
- seed ไม่ให้เมนู `/requests` กับ technician เลย
- สอง surface บังคับ policy ต่างกัน = ช่องโหว่ ไม่ใช่ policy

**ผลข้างเคียง:** technician/auditor ที่เคยเห็นคิวทั้งหมดจะเห็นแค่ของตัวเอง ถ้าต้องการให้ดูคิวได้จริง คำตอบคือให้ role `approver` ไม่ใช่ไปลดความเข้มของ controller

### V21 — approver เปลี่ยน status request ที่ `warehouseId=null` ของคนอื่นได้

**สิ่งที่พบ:** `scopeRequestWarehouse` เรียก `next()` ให้ทุกคนที่ไม่ใช่เจ้าของ เมื่อ `warehouseId === null`

**หลักฐานที่ชี้ขาด:** มันทำสำเร็จไม่ได้อยู่แล้ว — `requestController.ts:290` โยน `'Request warehouse not found'` เมื่อ approve โดยไม่มี warehouse และ `:351` ก็โยนเหมือนกันเมื่อ reject และมี items ดังนั้นมันคือ 400 ที่แต่งตัวเป็น "ผ่าน authorization" และที่แย่กว่าคือ**เจ้าของถูกปฏิเสธ 404 คนเดียว** ซึ่งกลับด้าน

**ตัดสิน:** เฉพาะ admin tier ผ่าน guard; คนอื่นได้ 404 (แยกไม่ออกจาก request ที่ไม่มีจริง)

### V22 — stock-transfers disclosure

**สิ่งที่พบ:** `POST /api/stock-transfers` อ่าน stock level ของคลังต้นทาง แล้วสะท้อน `available` กลับใน 400 response

**ตัดสิน:** บังคับ source-warehouse scope ก่อนอ่าน stock
- **ไม่** เช็ค destination โดยเจตนา — การรับของเข้าคือจุดประสงค์ของการโอน และ `PATCH /:id` บังคับ source scope อยู่แล้วก่อนของจะเคลื่อน
- ถ้าบังคับ destination ด้วย จะบล็อกเคสปกติ "ส่งของเข้าคลังกลาง"

### V20/V21 รวม — ข้อสรุปเรื่อง visibility

ทั้งสองข้อคือ policy เดียวกันคนละด้าน: ใครเห็นอะไร และใครแตะอะไรได้ คำตอบที่ consistent คือ **approver tier = ผู้ดูแลคลัง** ไม่ใช่ role ที่มีชื่อฟังดูมีสิทธิ์
