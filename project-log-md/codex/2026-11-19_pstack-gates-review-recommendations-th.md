# ทบทวนผล Pstack gates และข้อเสนอแนะก่อนเปิดใช้ระบบคลัง HR-IMS

**ผู้ทบทวน** Codex · 19 พฤศจิกายน 2569  
**เอกสารที่ทบทวน** Perch (Quill) · 19 พฤศจิกายน 2569 เวลา 00:06 น. ประเทศไทย  
**ขอบเขต** ตรวจเอกสารและสถานะ Git แบบอ่านอย่างเดียว ผลทดสอบด้านล่างอ้างจาก Perch

## ข้อสรุปสำหรับเจ้าของโครงการ

ความคืบหน้าสำคัญคือ `npm run test:authz` ผ่าน **249/249 และ exit 0** ตาม handoff ล่าสุด งานนี้เคยไม่ผ่านในเครื่องเมื่อ 18 พฤศจิกายน ให้ปรับสถานะเป็น **ผ่านตามรายงานของ Perch** และขอหลักฐานผูกกับชุดการเปลี่ยนแปลงที่จะส่งตรวจ ผล unit 76/76, Vitest 517/517 และ typecheck ทั้งสองฝั่งเป็นผลที่ Perch รายงานเช่นกัน

ยังขาดหลักฐานจาก TiDB ทดสอบว่าการลง migration การเปลี่ยนยอดพร้อมกัน และการย้อนกลับเมื่อเกิดข้อผิดพลาดให้ผลถูกต้อง งานรับรองสิทธิ์ผู้อนุมัติยังรอเจ้าของระบบ ส่วนการกระทบยอดด้วยบัตรคุมวัสดุยังรอยอดยกมาที่คลังนำร่องรับรอง จึงเสนอให้ส่งตรวจเป็นร่างเมื่อได้รับอนุญาต และใช้ผลตรวจ TiDB กับการตัดสินใจของเจ้าของระบบประกอบการอนุมัติเปิดใช้จริง

## จุดปรับปรุงใน handoff

| ระดับ | ข้อสังเกต | ข้อเสนอแนะและเกณฑ์ตรวจรับ |
| --- | --- | --- |
| สูง | **ผลทดสอบยังผูกกับชุดเปลี่ยนแปลงได้ไม่ชัด** การตรวจ Git แบบอ่านอย่างเดียวพบ HEAD `9f5c2b6` และ handoff ระบุว่างานยังไม่ได้ commit ผล 249/249 และ 517/517 จึงยังต้องอ้างถึง snapshot ที่มีการเปลี่ยนแปลงจริง | บันทึก HEAD พร้อมรายการไฟล์ที่แก้และไฟล์ใหม่ หรือผูกผลกับ commit เมื่อได้รับอนุญาต แนบคำสั่ง โฟลเดอร์ที่รัน โปรไฟล์ทดสอบแบบไม่เปิดเผยค่าลับ เวลา ผลสรุป และ exit code ระบุชื่อสองกรณีที่ทำให้ Vitest เพิ่มจาก 515 เป็น 517 หรืออธิบายความต่างของการเลือกชุดทดสอบจากหลักฐาน |
| สูง | **สถานะเกตบางตัวคลุมเครือ** `interrogate` เชื่อมต่อไม่สำเร็จทั้งสามครั้ง ส่วน `thermos` โหลดเนื้อหาสกิลได้แต่ไม่มี subagent ที่รองรับ `babysit` ทำงานในโหมดตรวจในเครื่องก่อนมี PR | ระบุ `interrogate` ว่าถูกขัดจังหวะ, `thermos` ว่ารันการประเมินไม่ได้ใน runtime นี้ และ `babysit` ว่าตรวจในเครื่องแล้วกับสถานะ PR ที่ยังไม่มี หากเจ้าของต้องการผล review เพิ่ม ให้ย้ายไปรันใน runtime ที่รองรับหรือมอบหมายผู้ทบทวนและบันทึกผลกับ revision เดียวกัน |
| สูง | **รายการค้างตกหล่นจากรายงานก่อนหน้า** handoff ล่าสุดไม่ระบุการรับรองยอดยกมาและการเทียบผลรายงาน SQLite/TiDB ข้ามเดือนตามเวลาไทย | นำสองรายการกลับเข้าเช็กลิสต์ หรือแนบหลักฐานพร้อมผู้รับผิดชอบและวันที่ที่ปิดจริง ให้ยอดยกมารายคลังและรายวัสดุมีเวลาเริ่มใช้และผู้รับรอง ส่วนผลเทียบสองฐานข้อมูลให้ใช้ข้อมูลเดียวกันและมีค่าคาดหมายจากข้อมูลตั้งต้น |
| กลาง | **timeout 60 วินาทีอาจบดบังความช้าของการตั้งค่าเทสต์** handoff อธิบายว่าเพิ่มเพื่อ dynamic import ภายใต้ fork pool แต่ไม่มีเวลารันรายกรณีหรือการแยกช่วงที่ช้า | เก็บเวลาของไฟล์ `login-form.test.tsx` ทั้งแบบรันเดี่ยวและทั้งชุดภายใต้ fork pool เดียวกับ CI รวมช่วง dynamic import และเวลารวมอย่างน้อยหลายรอบ บันทึกเหตุผลที่เลือก 60 วินาที และทบทวนเพดานหลังทราบว่าความช้าอยู่ที่การตั้งค่า การโหลดโมดูล หรือการรันเทสต์ |
| กลาง | **หลักฐาน blast radius และการเก็บสกิลท้องถิ่นยังไม่พอสำหรับส่งตรวจ** handoff ให้ผลรวมเทสต์และบอกว่าเก็บสกิลส่วนเกิน 53 ตัวไว้ ขณะที่ Git แสดง `.perch/` เป็น untracked และ `.gitignore` ถูกแก้ | ระบุขอบเขตการทดสอบของ Next.js, Express, schema และ UI ที่ได้รับผล พร้อมชื่อ targeted suite ก่อนสร้างชุดส่งตรวจให้ตรวจรายการไฟล์แบบระบุพาธและพิจารณา `.gitignore` แยกจากงานคลัง สำหรับการตั้งค่าสกิล ให้บันทึกเวอร์ชัน Perch CLI, pstack `0.9.139`, รายชื่อเจ็ดสกิลที่ใช้และขั้นตอนกู้คืน เอาข้อจำกัด 40 สกิลไปใช้อ้างอิงกับ runtime ที่พบปัญหา |

## ลำดับงานและหลักฐานที่ควรปิด

| ช่วง | ผู้รับผิดชอบที่เสนอ | หลักฐานตรวจรับ |
| --- | --- | --- |
| 1. เตรียมชุดส่งตรวจ | ทีมแอปพลิเคชัน | ระบุ snapshot และเก็บผล unit, authz, Vitest, typecheck กับ diff check บนชุดเดียวกัน ระบุสถานะของเกตที่รันไม่จบและตรวจรายการไฟล์ก่อนเปิด draft PR เมื่อได้รับอนุญาต |
| 2. ยืนยันขอบเขตการอนุมัติและคืนวัสดุ | เจ้าของระบบร่วมกับทีมแอปพลิเคชัน | รับรองตารางสิทธิ์ดูและตัดสินคำขอ ตรวจผลตามตารางบน Next.js และ Express เจ้าของระบบยืนยันว่าการคืนผ่าน Express มีผู้ใช้งานหรืออยู่ในขอบเขตรอบนี้หรือไม่ พร้อมผลตรวจเส้นทางจริงหากอยู่ในขอบเขต |
| 3. ทดลอง migration และการเปลี่ยนยอดบน TiDB ทดสอบ | ผู้ดูแลฐานข้อมูลและทีมแอปพลิเคชัน | แนบผลรัน migration บน schema เดิม ผลรันซ้ำและขั้นตอนกู้คืน ตรวจยอดคงเหลือ ยอดจอง ประวัติ และสถานะเมื่ออนุมัติคำขอเดียวกันจากสองช่องทาง เมื่อคนละคำขอแตะสต็อกเดียวกัน และเมื่อเกิดข้อผิดพลาดกลางรายการ ตรวจว่าการปรับยอดรอบเดียวกันมีผลครั้งเดียว |
| 4. ตรวจรายงานและเตรียมคลังนำร่อง | ทีมรายงานและเจ้าของคลัง | เทียบยอดรายเดือน SQLite/TiDB ตรงรอยต่อเที่ยงคืนไทย วัด p95 ก่อนและหลังด้วยข้อมูลและภาระงานเดียวกัน คลังรับรองยอดยกมาและแสดงผลทดลองกระทบยอด ณ เวลาเดียวกันก่อนใช้บัตรคุมเพื่อกระทบยอด |
