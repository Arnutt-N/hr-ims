## ข้อเสนอเพื่อการตัดสินใจ

ให้ตรวจรับการเปลี่ยนยอดสต็อก สิทธิ์ผู้อนุมัติ และ migration บนสภาพแวดล้อมทดสอบก่อนพิจารณาเปิดใช้จริง จากนั้นให้คลังนำร่องรับรองยอดยกมาก่อนใช้บัตรคุมวัสดุเพื่อกระทบยอด การวัดประสิทธิภาพทำคู่ขนานได้ แต่ควรใช้ผลจริงก่อนสรุปว่าการปรับรายงานและหน้าคำขอช่วยลดเวลาโหลด

Perch รายงานว่าได้เพิ่มบัตรคุมวัสดุ ใบเบิกพิมพ์ได้ การแบ่งหน้าคำขอ รายงานตามเวลาไทย และรอบตรวจนับแล้ว รวมถึงเพิ่มประวัติเบิก ยืม และคืนในทั้งสองฝั่ง และใช้การอัปเดตสถานะแบบมีเงื่อนไขเพื่อป้องกันการเปลี่ยนยอดซ้ำ ผลที่รายงานคือ frontend 515/515 สองรอบ, backend unit 76/76, request controller 7/7, typecheck ทั้งสองฝั่ง และ Prisma validate/generate ผ่าน ส่วน `test:authz` ยังไม่ผ่านและ migration ยังไม่เคยรันกับฐานข้อมูลทดสอบตามบันทึก รายงานฉบับนี้ประเมินจากเอกสารส่งต่อและไม่ได้รันทดสอบซ้ำ

## 1. งานที่ควรปิดก่อนพิจารณาปล่อย

| ลำดับ | ข้อเสนอแนะ | เกณฑ์ตรวจรับ |
| --- | --- | --- |
| 1 | **กำหนดขอบเขตผู้อนุมัติร่วมกัน** ให้เจ้าของระบบยืนยันสิทธิ์ดูรายการและสิทธิ์อนุมัติหรือปฏิเสธ แยกตามบทบาท หน่วยงาน คลัง และความเป็นเจ้าของคำขอ ตามที่นโยบายกำหนด | มีตารางสิทธิ์ที่เจ้าของรับรอง ใช้ชุดกรณีเดียวกันตรวจ Next.js และ Express กรณีที่อนุญาตทำงานสำเร็จ กรณีที่ถูกปฏิเสธไม่เปลี่ยนสถานะ ยอดสต็อก หรือประวัติธุรกรรม |
| 2 | **ยืนยันผลทดสอบสิทธิ์บนสภาพแวดล้อมที่จัดไว้** ให้ผู้ดูแลจัดค่าทดสอบตามขั้นตอน CI และเก็บผลรันพร้อม revision ใช้ผลที่รายงานไว้เป็นข้อมูลประกอบการวินิจฉัย | `npm run test:authz` ผ่านและจบได้ตามปกติ เก็บจำนวนเทสต์ที่ผ่านและล้มเหลว หากยังมี open handles ให้บันทึกต้นเหตุและแก้การปิดทรัพยากร ค่า secret อยู่ในระบบจัดการค่าของสภาพแวดล้อมทดสอบ |
| 3 | **ทดลอง migration กับ schema เดิมบน TiDB ทดสอบ** ใช้สำเนาข้อมูลทดสอบที่เป็นตัวแทนและบันทึกวิธีสำรองหรือกู้คืนก่อนเริ่ม | ตารางตรวจนับ ดัชนี และ foreign key ตรงกับ schema ใช้งานจริง ข้อมูลเดิมครบ รันซ้ำได้ตามที่ออกแบบ และเปิดรอบ บันทึกผล อนุมัติ และปรับยอดผ่านช่องทางปกติได้ครบ |
| 4 | **ตรวจการเปลี่ยนยอดพร้อมกันและ rollback บนฐานข้อมูลจริง** ครอบคลุมการอนุมัติคำขอเดียวกันจากทั้งสองช่องทาง การปรับยอดรอบเดียวกัน คำขอคนละรายการที่แก้สต็อกรายการเดียวกัน และความล้มเหลวระหว่างปรับยอด | คำขอหรือรอบเดียวกันมีผลครั้งเดียว ยอดคงเหลือตรงกับธุรกรรมที่สำเร็จ ยอดจองสอดคล้องกับยอดคงเหลือตามกติกาคลัง และเมื่อเกิดข้อผิดพลาด ยอด สถานะ ประวัติ และ audit ย้อนกลับพร้อมกัน ทดสอบทั้งการเคลื่อนไหวก่อนนับและระหว่างนับกับปรับยอด |
| 5 | **ยืนยันเส้นทางคืนวัสดุของ Express** ตรวจผู้เรียกและข้อมูลจริงที่ส่งเข้า `PATCH /:id/status` สำหรับคำขอชนิด `return` | หากมีผู้เรียกใช้งาน ให้ทดสอบผ่าน route จริงและเทียบผลกับ Next.js โดยยอดคลังและยอดรวมเพิ่มตามจำนวน ประวัติเป็น `inbound` อ้างถึงคำขอ และระบุผู้อนุมัติกับผู้ขอในส่วนที่เกี่ยวข้อง หากยังไม่มีผู้เรียก ให้บันทึกสถานะและให้เจ้าของระบบตัดสินใจว่าต้องรองรับช่องทางนี้ในรอบเปิดใช้หรือไม่ |

## 2. งานที่ต้องปิดก่อนใช้บัตรคุมวัสดุกระทบยอด

1. **กำหนดเวลาเริ่มบันทึกครบของคลังนำร่อง** ให้เจ้าของคลังยืนยันวันที่และเวลาเริ่มใช้ตามเวลาไทย แล้วตรวจว่าค่า `STOCK_CARD_CUTOVER_DATE` และเงื่อนไขกรองวันที่ใช้ขอบเขตเดียวกัน หากระบบเก็บได้เพียงวันที่ ให้กำหนดวิธีจัดการรายการระหว่างวันก่อนรับรองยอด
2. **รับรองยอดยกมา** เก็บยอดรายคลังและรายวัสดุ ณ เวลาเริ่มใช้ พร้อมหน่วยนับ ผู้รับรอง และหลักฐานการตรวจนับ หากยังรอรับรอง ให้ใช้บัตรคุมเพื่อดูรายการเคลื่อนไหวที่บันทึกไว้และยอดปัจจุบัน
3. **ทดลองกระทบยอด** เทียบยอดยกมา + รับเข้า − จ่ายออก + ผลสุทธิจากการปรับยอด กับ `StockLevel.quantity` ณ เวลาเดียวกัน ใช้กรณีตัวอย่างที่มีรายการก่อนและหลังเวลาเริ่มใช้ การคืน และการปรับยอด เก็บรายการส่วนต่างพร้อมคำอธิบายจนตรวจสอบย้อนกลับได้

## 3. ยืนยันคุณภาพรายงานและประสิทธิภาพ

| งาน | วิธีตรวจและผลที่ต้องเก็บ |
| --- | --- |
| ความถูกต้องข้ามฐานข้อมูล | ใช้ข้อมูลชุดเดียวกันบน SQLite และ TiDB เทียบยอดรวมและยอดรายเดือนกับค่าที่คำนวณจากข้อมูลตั้งต้น รวมรายการก่อนและหลังเที่ยงคืนไทยตรงรอยต่อเดือน |
| การแบ่งหน้าคำขอ | ใช้ข้อมูลที่เวลา `createdAt` ซ้ำกัน ตรวจลำดับด้วย `id` การเปลี่ยนหน้า ตัวกรอง จำนวนรวม และความหมายของ pending badge เมื่อตัวกรองเปลี่ยน |
| ประสิทธิภาพ | วัด p50/p95 ของหน้าคำขอและรายงานก่อนและหลังด้วยชุดข้อมูล ภาระงาน และเงื่อนไขแคชเดียวกัน บันทึกขนาดข้อมูล จำนวนตัวอย่าง และ revision แยกผลของสองหน้า ให้เจ้าของระบบตกลงเป้าหมายก่อนตัดสินผล |

## 4. หลักฐานสำหรับการตรวจรอบถัดไป

- **ทีมแอปพลิเคชัน** แนบผลทดสอบที่ระบุ revision และสภาพแวดล้อม พร้อมผลตรวจสิทธิ์ การเขียนพร้อมกัน และความสอดคล้องของสองช่องทาง
- **ผู้ดูแลฐานข้อมูล** แนบบันทึก migration การรันซ้ำ วิธีคืนสภาพ และผลเทียบ SQLite กับ TiDB
- **เจ้าของระบบและคลังนำร่อง** ยืนยันขอบเขตผู้อนุมัติ การรองรับเส้นทางคืนวัสดุ และยอดยกมาที่ใช้กระทบยอดตามลำดับ
- **การส่งตรวจโค้ด** Perch ระบุว่างานยังอยู่ใน working tree โดยยังไม่ได้ commit, push หรือเปิด PR ให้รวบรวมรายการเปลี่ยนแปลงและหลักฐานตามเกณฑ์ข้างต้นเมื่อเจ้าของโครงการอนุญาตให้เปิด draft PR
